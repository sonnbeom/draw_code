# 전체 파이프라인: 도면 PDF → BOM xlsx

## 문제 정의
- 입력: 도면 PDF (벡터). 글자가 텍스트가 아니라 **선(CAD 스트로크 폰트)**으로 그려져 있다
- 출력: BOM (모부품 + 자부품 행)을 case_XXXX.xlsx와 같은 구조로
- 데이터: PDF 820개 + 정답 json

## 전체 흐름
```
                 ┌──────── 기하 규칙 (ML 없음) ────────┐   ┌──── ML ────┐
PDF → ① 선 추출 → ② 표 찾기 → ③ 칸 나누기 → ④ 규칙 처리 → ⑤ 글자 읽기 → ⑥ 조립 → ⑦ xlsx
                                                              ▲
                                    학습: train PDF → 자동 라벨링 → 카드 → 모델
                                    평가: test PDF → ①~⑦ → json과 비교
```

## ① 선 추출 ([02](02_PDF구조와_OCR.md))
**문제.** 텍스트 추출이 안 된다. 글자를 어떤 형태로 읽을까?

| 후보 | 장점 | 단점 |
|---|---|---|
| 이미지 + OCR | 기존 도구 사용 | 표 구조(칸 위치) 손실, 작은 글자 해상도 문제 |
| **선 좌표** | 좌표 정확, 표 구조와 글자를 같은 데이터로 처리 | 분류기를 직접 만들어야 함 |

**결정.** 선 좌표. 출력 = 선분 목록 `(x1, y1, x2, y2, 색)`
- 선분은 `m`/`l`만 있음 (곡선·사각형 없음)
- 색: 검정 `0 0 0`, 파랑 `0 0.314 1` (리비전 삼각형·안 숫자), `0 0.353 0.706` (로고, 치수선)

## ② 표 찾기 ([03](03_표_찾기.md))
**문제.** 선 수천 개 중 BOM 표는 어디인가? 표제란·리비전 기록란도 같은 격자 모양이다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 헤더 글자로 판별 | 직관적 | 글자를 읽으려면 모델이 필요한데, 모델 학습엔 BOM 표가 필요 (순환 의존) |
| ML 표 검출 | 범용 | 학습 데이터·비용 큼 |
| **기하 규칙 + 연결선** | 글자 없이 가능, 양식 고정이라 정확 | 양식이 바뀌면 규칙 수정 |

**결정.** 기하 규칙
```
길고 + 수평/수직 (허용 오차)         → 글자·도형·헤더 사선 제외
끝점이 맞닿은 묶음                   → 표 후보 (BOM, 표제란, 리비전 기록란, 모부품 박스)
모부품 박스에서 나온 연결선이 닿는 표  → BOM 표 (안 닿으면 BOM 아님)
화살표가 닿는 x 위치                 → 모부품 ↔ 수량 열 매핑
```
- 헤더 양식 3종(standard / slash_pno / slash_qty_assy): 헤더를 읽지 않으므로 별도 처리 없음
- 취소선도 "길고 수평"이라 후보에 섞임 → ④에서 구분

## ③ 칸 나누기 ([03](03_표_찾기.md), [13](13_모부품_박스.md))
**문제.** 표 안 선들을 칸별로 나눠야 한다.

**결정.** 격자 가로선 사이 = 행, 세로선 사이 = 열. 칸마다 그 안의 짧은 선을 모은다. 헤더 행은 건너뛴다. 모부품 박스도 칸으로 취급한다.

## ④ 규칙 처리 ([06](06_취소선.md), [12](12_리비전_삼각형.md), [13](13_모부품_박스.md))
**문제.** 글자가 아닌 선(취소선, 리비전 삼각형, 연결선)이 글자와 섞여 있다. 그대로 두면 글자 나누기가 깨진다.

**결정.** 규칙으로 찾아서 **기록하고 지운 뒤** 글자를 읽는다.

| 대상 | 찾는 법 | 기록 |
|---|---|---|
| 취소선 | 행 가운데 높이에서 글자를 가로지르는 긴 수평선 | `[DEL]` |
| 리비전 삼각형 | 닫힌 세 선 + 정삼각형 + 밑변 수평 + 크기 (변 ÷ 글자 높이 비율) | 안 숫자를 내림차순 → `(02,01)` |
| 연결선 | ②에서 이미 찾음 | 없음 (모부품 품명 줄을 가로질러서 지움) |

- 삼각형 크기는 도면마다 다름 (변 15.6~25) → 절대값 대신 글자 높이 대비 비율
- 삼각형 색(파랑/검정)은 구분하지 않음
- 삼각형 소속: 같은 y에서 **오른쪽으로 가장 가까운 대상** (모부품 박스 → 모부품 rev, 표 행 → 행 no)

## ⑤ 글자 읽기 ([04](04_글자_나누기.md), [07](07_정규화.md), [08](08_래스터화.md), [09](09_모델_선택.md), [11](11_데이터_품질.md))
**문제.** 칸 안의 선들을 문자열로 바꿔야 한다. 도면마다 글자 위치·크기가 다르고, 두 줄 품명도 있다.

| 순서 | 문제 | 결정 |
|---|---|---|
| 줄 나누기 | 두 줄 품명을 그냥 x 정렬하면 위·아래 줄 글자가 섞여 라벨이 밀림 | y범위가 겹치면 같은 줄, 줄마다 x 정렬 후 위 줄부터 이어 붙임 |
| 글자 나누기 | 선들을 글자 단위로 묶어야 함 | 이어진 선 + x범위 겹침 = 한 글자, 큰 간격 = 띄어쓰기 |
| 정규화 | 같은 글자도 위치·크기가 달라 다른 숫자가 됨 | x는 글자 왼쪽 끝, y는 줄 바닥 기준, 줄 높이로 나눔. "-"처럼 높이 0인 글자 때문에 **행 전체**의 바닥·높이를 씀 |
| 래스터화 | 글자마다 선 개수가 달라 입력 길이가 다름 | 16×16 격자 → 입력 256개 고정 |
| 분류 | 256개 숫자 → 글자 | 아래 모델 표 |

| 모델 후보 | 장점 | 단점 |
|---|---|---|
| k-NN | 학습 없음, 데이터 상태 진단 | 느림, 칸별 중요도 모름 |
| 최근접 중심 | 아주 빠름 | 0/O처럼 비슷한 글자에 약함 |
| **선형 (로지스틱 회귀/SVM)** | 구별되는 칸에 가중치, 빠름 | 복잡한 패턴엔 한계 |
| 신경망 | 표현력 높음 | 이 규모엔 과함 |

**결정.** 선형 = 본 모델, k-NN = 점검용, 신경망 사용 안 함. CAD 폰트라 모양이 일정해서 선형으로 충분하다. 둘 다 낮으면 데이터 문제, k-NN만 높으면 모델 문제.

## ⑥ 조립 ([12](12_리비전_삼각형.md), [13](13_모부품_박스.md))
**문제.** 읽은 문자열과 규칙 처리 결과를 출력 구조로 묶어야 한다. 모부품 품명은 박스 밖에 있다.

**결정.**
- **표 행:** `no` (+ ` (02,01)`, + ` [DEL]`) / `part_no` / `part_name` / `quantities` {모부품 품번: 값}
- **모부품:** 박스 안 칸 → `part_no` (+ `index_no`, slash_pno 일부에만 있음) / 박스 y범위 + 박스 오른쪽 선 (연결선 제외) → `part_name` / 왼쪽 삼각형 → `rev`
- `[BLUE]`는 출력하지 않음

## ⑦ xlsx 출력
case_XXXX.xlsx와 같은 구조로 쓴다 (셀 배치는 구현 때 샘플로 확인).

## 학습 ([05](05_라벨_학습데이터.md), [09](09_모델_선택.md), [11](11_데이터_품질.md))
**문제.** 글자 카드 수만 장에 정답을 붙여야 한다. 나누기가 틀리면 라벨도 틀린다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 사람이 라벨링 | 정확 | 양이 많아 불가능 |
| **json 정답으로 자동 라벨링** | 대량 자동 생성 | 나누기 오류가 라벨 오류로 번짐 |

**결정.** 자동 라벨링 + 2단 검사
```
train PDF → ①~⑤ 글자 나누기 → json 정답과 비교
  1차 개수 검사: 글자 묶음 수 ≠ 정답 글자 수 → 그 칸 버림
  2차 크기 검사: 같은 글자인데 정규화 후 폭·높이가 크게 다름 → 버림
→ k-NN (점검) + 선형 모델, 하이퍼파라미터는 val로
```
- 분할: **PDF 단위** train/val/test = 70/15/15 (글자 단위로 섞으면 같은 도면이 양쪽에 들어가 점수가 부풀려짐)
- 820쌍만 사용 (0821~1000은 PDF 없음)

## 평가 ([14](14_평가.md))
**문제.** 글자 정확도 99%여도 12글자 품번 칸은 0.99¹² ≈ 89%. 단위에 따라 점수가 크게 다르고, 점수 하나로는 틀린 원인을 모른다.

**결정.**
| 항목 | 방법 |
|---|---|
| 데이터 | test PDF, 마지막에 한 번만 |
| 점수 | **행 정확도 (주 점수)** / 칸 정확도 (칸 종류별) / 글자 정확도 (모델 진단) |
| 행 짝짓기 | no로 짝지음 (도면 안에서 no 중복 0건). no 오독 대비 못 짝지은 행은 품번·행 순서로 2차 짝짓기 |
| 버리기 | 안 버림. 개수가 안 맞아도 틀린 걸로 셈 (버리면 쉬운 칸만 채점하게 됨) |
| 원인 가르기 | 위 단계부터: 행·열 수 다름 → 표 찾기 / 글자 수 다름 → 나누기 / 내용만 다름 → 모델 |
| 쪼개 보기 | header_style별, 페이지 크기별, 칸 종류별 |

## 구현 순서
| 순서 | 만들 것 | 확인 방법 |
|---|---|---|
| 1 | ① 선 추출 | matplotlib으로 다시 그려 원본과 비교 |
| 2 | ② 표 찾기 | BOM 표만 색칠해서 그려 보기, 행 수 = json `num_items` |
| 3 | ③ 칸 나누기 + ④ 규칙 처리 | DEL·rev가 json과 일치 |
| 4 | 자동 라벨링 → 카드 저장 | 버린 칸 비율 |
| 5 | ⑤ 정규화·래스터화·모델 | val 글자 정확도, k-NN vs 선형 |
| 6 | ⑥ 조립 + ⑦ 출력 + 평가 | test 행 정확도, 단계별 원인 개수 |

## 구현 때 확인할 것
