# 02. PDF 구조와 글자 읽기 방식

## 문제 1. 모델 하나로 PDF → xlsx를 통째로 풀 수 있나?

**결정.** 통째로 풀지 않고 **단계를 나눈다**: 글자 얻기 / 표 찾기 / 크기 차이 처리. 단계마다 검증할 수 있어 실무에 맞다.

**PDF가 글자를 저장하는 방식**
| 방식 | 내용 | 우리 PDF |
|---|---|---|
| 텍스트 | "'88114'를 써라". 복사하면 글자가 나옴 | 아님 |
| 선 | "(100,200)→(105,210) 선을 그어라"의 반복 | **전부 이 방식** |

- CAD의 선 글꼴(SHX 스트로크 폰트)을 PDF로 내보내면 글자가 선 그리기 명령으로 바뀐다
- 컴퓨터에게 "이건 8이다"라는 정보는 없고 좌표만 있다 → **머신러닝으로 글자를 인식해야 한다**

## 문제 2. 이미지 OCR vs 선 좌표

| 후보 | 장점 | 단점 |
|---|---|---|
| 이미지 + OCR | 기존 도구 사용 | 행·열 대응이 사라짐, 읽는 순서가 꼬임, 큰 도면은 해상도 부족 |
| **선 좌표** | 확대·축소와 무관하게 정확, 표 구조를 같은 데이터로 처리 | 분류기를 직접 만들어야 함 |

- 문제는 **① 찾기(검출) → ② 읽기(인식)** 순서. 찾기가 틀리면 읽기는 소용없다
- OCR은 글자만 읽고 어느 행·열인지는 따로 알아내야 한다
- 해상도: case_0306(가로 11,905pt)을 2000px로 만들면 약 6pt = 1px → 글자가 1~2픽셀

**결정.** 선 좌표 → 아래 문제 3에서 **글자 읽기만 OCR로 변경** (2026-11-17)

## 문제 3. 글자 읽기를 OCR로 바꾸나

OCR은 "이 이미지에 어떤 글자가 어디 있다"만 준다.
| 필요한 정보 | OCR | 선 좌표 |
|---|---|---|
| 글자 | 됨 (정확도는 미확인) | 분류기를 직접 만들어야 함 |
| 몇 행 몇 열 | 위치 상자만 줌, 칸 경계는 모름 | 칸 선에서 바로 나옴 |
| 취소선 `[DEL]` | 무시하거나 글자를 망가뜨림. DEL 정보는 안 나옴 | 규칙으로 찾고 지움 |
| 리비전 △ | 안 숫자는 읽힐 수 있으나 삼각형 존재·소속은 모름 | 규칙 |
| 상위↔하위 연결 | 선은 글자가 아니라 결과에 없음 | 끝점 따라가기 |

| 후보 | 장점 | 단점 |
|---|---|---|
| 선 좌표 + 직접 분류기 (기존) | 외부 도구 없음 | 나누기·정규화·래스터화·자동 라벨링·모델을 다 만들어야 함 |
| **선 좌표(구조) + OCR(글자)** | 글자 읽기를 기성 모델이 대신함. 머리글을 읽을 수 있게 됨 ([03](03_표_찾기.md)) | OCR 엔진 의존. 이 폰트 정확도 미확인 |
| OCR만 | 단순해 보임 | 행·열·DEL·연결을 결국 선으로 다시 해야 함 |

**결정.** 위치·구조는 선, 글자 내용은 OCR. 바뀌는 건 ⑤ 글자 읽기 한 단계뿐이다 ([15](15_전체_파이프라인.md)).
- **OCR 전에 방해 선을 지운다.** 취소선·삼각형·연결선을 기록하고 뺀 나머지 획만 그려 OCR에 넣으면 깨끗한 글자 이미지가 된다 (PDF를 그대로 렌더링하지 않아도 됨)
- **위치를 버리지 않는다.** 텍스트만 뽑으면 어느 칸인지 사라져 조립·연결이 불가능하다. 칸 단위로 OCR하면 칸 좌표가 곧 위치
- 큰 도면도 표 영역만 잘라(clip) 그리면 선명하다 (페이지 전체 한 장이면 글자 1~2px)
- 미정: OCR 엔진, 입력 이미지 만드는 법, 칸 단위 vs 표 단위

## 문제 4. 글자 학습이 필요한가 (폰트 포함)

원래 머신러닝은 **글자 인식 하나** 때문이었다. OCR이 이걸 대신한다.

| 학습 데이터 후보 | 필요한 것 | 장점 | 단점 |
|---|---|---|---|
| A. json 자동 라벨링 | 샘플 PDF + json | 이미 있음 | 나누기 오류 → 라벨 오류 |
| B. 폰트 파일로 생성 | 같은 **획** 폰트 (외곽선 TTF는 모양이 다름) | 라벨 오류 없음 | 파일 확보 필요 |
| C. 글자별 견본 수동 수집 | 사람 시간 (40~50종) | 폰트·json 불필요 | 수작업 |

- 같은 폰트 → 같은 글자는 크기·위치만 다르고 획은 동일. 데이터가 많이 필요한 문제가 아님
- 테스트 도면과 샘플은 같은 폰트 → 폰트 파일 불필요 (A로 충분)

**결정.** 글자 직접 학습은 **보류**. OCR 그대로 샘플 val에서 **칸 정확도**(특히 품번)를 재고, 부족하면 틀린 글자를 분석해 OCR 미세조정 또는 기존 분류기 설계([07](07_정규화.md)~[11](11_데이터_품질.md))를 꺼낸다. 글자 99%여도 품번 칸은 약 89%라서 기준은 칸 단위로 잡는다 ([14](14_평가.md)).
- 머신러닝은 대신 "결과를 믿을 수 있나" 층에 쓴다: 칸 신뢰도([14](14_평가.md) 5절), 표 종류 분류([03](03_표_찾기.md) 6절)
