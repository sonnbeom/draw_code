# 11. 데이터 품질: 점수가 낮을 때 원인 가르기

## 문제
점수가 낮으면 원인이 둘이다.
```
[데이터 만들기]                                        [모델]
표 찾기 → 글자 분리 → 자동 라벨링 → 정규화 → 래스터화 → 학습 → 점수
       └──────────── 원인 1: 데이터 ───────────┘      └ 원인 2: 모델 ┘
```

## 결정 1. k-NN을 점검용으로 같이 돌린다
- k-NN은 학습 과정이 없고 설정도 k 하나 → 점수 ≈ **데이터가 얼마나 깨끗한가**
| k-NN | 선형 | 해석 | 고칠 곳 |
|---|---|---|---|
| 90% | 90% | 데이터가 깨짐 | 글자 분리, 라벨링, 정규화 |
| 99% | 90% | 데이터는 깨끗, 모델이 못함 | 모델 설정 |
| 99% | 99% | 둘 다 좋음 | 선형 채택 |
- k=1로 틀린 글자의 이웃을 그려 보면 "라벨은 3인데 그림은 8" 같은 **잘못된 카드**를 직접 찾을 수 있다

## 원인 1의 종류
데이터 문제 = 카드 앞면(그림)이나 뒷면(정답)이 잘못 만들어진 것. 모델을 바꿔도 안 고쳐지고 앞 단계 코드를 고쳐야 한다.

| # | 사고 | 잘못되는 것 | 해결 |
|---|---|---|---|
| 1 | 나누기 오류 | 정답지 | 크기 검사 |
| 2 | 라벨 밀림 (두 줄 품명) | 정답지 | 줄 나누기 |
| 3 | 정규화 오류 ("-"만 있는 칸) | 그림 | 행 전체 기준 |
| 4 | 래스터화가 너무 거칢 | 그림 | 16×16 ([08](08_래스터화.md)) |

## 1. 나누기 오류 → 크기 검사
**문제.** 실수 두 개가 우연히 개수를 맞추면 개수 검사를 통과한다.
```
정답 "88250"
잘못 나눔: [8] [8] [25] [(] [)]    ← "2"와 "5"가 붙고 "0"이 둘로 쪼개짐
개수 5 == 5 → 통과 → [25]="2", [(]="5", [)]="0" 틀린 카드가 섞임
```
- 글자가 닿는 원인: 취소선 잔여, 좁은 글자 간격(case_0001), rev 삼각형

**결정. 크기(폭·높이) 검사 추가.** 같은 CAD 폰트라 같은 글자는 정규화 후 폭·높이가 거의 같다.
| 묶음 | 라벨 | 실제 폭×높이 | 정상 | 판정 |
|---|---|---|---|---|
| `[8-]` | "8" | **1.0**×1.0 | 0.6×1.0 | 너무 넓음 ✗ |
| `[(]` | "-" | 0.3×**1.0** | 0.5×0.05 | 키가 큼 ✗ |
| `[)]` | "0" | **0.3**×1.0 | 0.6×1.0 | 너무 좁음 ✗ |
(설명용 숫자)
- 정상 범위는 데이터 자체로 안다: "8" 카드 대부분은 맞으니 동떨어진 값 = 이상치 → 그 칸 버림
```
자동 라벨링 검사
 1차: 묶음 개수 == 글자 수
 2차: 묶음 크기가 그 라벨의 정상 범위 안
```

## 2. 라벨 밀림 → 줄 나누기
**문제.** 두 줄 품명 (case_0001 12행: `BRKT-DIVE 3RD CUSH OTR, RH` + `(IMS)`)을 x로만 정렬하면 두 줄이 섞인다. 나누기는 완벽해서 개수 검사도 통과한다.
```
윗줄:   B(x=10) R(16) K(22) T(28) ...
아랫줄: ((x=9)  I(13) M(17) S(21) )(25)
x 정렬: ( B I R M S K ) T ...   → 라벨 전부 밀림
```

**결정. 줄 나누기 (line segmentation)**
```
① y범위가 겹치면 같은 줄 → ② 줄마다 x 정렬 → ③ 위 줄부터 이어 붙임 → ④ 라벨
```
- 글자 나누기(x범위 겹침)와 같은 아이디어를 y로 적용
- 한 줄 칸도 같은 처리 (줄이 1개 나올 뿐) → 한 줄/두 줄 구분 규칙 불필요
- `(`, `,`처럼 위아래로 삐져나와도 범위가 겹치기만 하면 같은 줄
- 위험: 줄 간격이 너무 좁으면 아랫줄 `(`가 윗줄과 겹칠 수 있음 → 구현 때 실제 줄 간격 확인

## 3. 정규화 오류 → 행 전체 기준
**문제.** 수량 칸의 "-" 혼자 (= 그 모부품엔 안 들어감)는 높이가 0이라 나누기 에러.
```
수량 칸 값 (PDF 820개):  "1" 12,106 / "-" 9,758 / "2" 6,680 / "3" 6,450 ...
→ 수량 칸 4개 중 1개. 드문 예외가 아님
"-" 혼자: y 최소 22, 최대 22 → (22 − 22) / 0 → 에러
```
- 품명 속 "-"(`BRKT-DIVE`)는 옆 글자가 높이를 정해 줘서 괜찮다

| 후보 | 문제 |
|---|---|
| "-"일 때만 옆 칸 값을 빌림 | 읽기 전이라 "-"인지 미리 알 수 없음 |
| **모든 칸이 행 전체 기준 사용** | - |

**결정.** 행마다 줄 바닥·줄 높이를 **행 전체**로 한 번 정하고 그 행의 모든 칸이 같은 기준을 쓴다
```
y
26 ─  ┐         ← "1" 꼭대기
22 ─  │    ───   ← "-"
20 ─  ┘         ← "1" 바닥 (행 줄 바닥)
(22 − 20) / 6 ≈ 0.33  → 줄의 1/3 높이에 가로선
```
- 높이뿐 아니라 **바닥도** 행 기준 (안 그러면 "-"가 바닥으로 내려가 "_"처럼 됨)
- 학습·실제 사용에서 같은 방법으로 그림이 만들어진다
- 수량이 전부 "-"인 행도 No.·품번 칸에 글자가 있어 괜찮다
- 두 줄 칸은 줄 나누기 후 **줄마다** 잰다
- 0.33은 칠할 좌표일 뿐, "-" 판단은 모델이 한다
| 글자 | 가로선 위치 |
|---|---|
| "-" | 가운데쯤 |
| "_" | 바닥 |
| "=" | 두 군데 |
