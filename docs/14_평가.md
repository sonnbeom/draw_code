# 14. 평가

## 문제
다 만든 뒤 "써도 되나?"와 "어디가 약한가?"를 숫자로 답해야 한다.

| 정할 것 | 결정 |
|---|---|
| 무엇 단위로 세나 | 아래 1 |
| 어느 데이터로 재나 | test PDF, 마지막에 한 번 ([09](09_모델_선택.md)) |
| 출력과 정답을 어떻게 짝짓나 | 아래 2 |
| 틀린 원인을 어떻게 가르나 | 아래 3 |

## 1. 점수 단위
**문제.** 단위가 커질수록 점수가 내려간다 (곱의 법칙).
| 글자 수 | 계산 | 칸이 통째로 맞을 확률 |
|---|---|---|
| 1 | 0.99 | 99% |
| 2 | 0.99 × 0.99 | 98% |
| 12 (품번) | 0.99¹² | **약 89%** |
- 글자 정확도 ≠ 칸 정확도. 행은 여러 칸이 모두 맞아야 하므로 더 낮다

**결정.** 세 단위를 모두 재되 역할을 나눈다
| 단위 | 역할 |
|---|---|
| **행 정확도** | **주 점수.** 사용자가 실제로 쓰는 단위 |
| 칸 정확도 (품번/품명/수량별) | 어느 칸이 약한지 |
| 글자 정확도 | 모델 자체 성능 |

## 2. 행 짝짓기
**문제.** 순서대로 짝지으면 행 하나만 놓쳐도 뒤가 전부 밀려 틀린 걸로 나온다.
```
정답          출력 (2행 놓침)
1 88100-A     1 88100-A   ✓
2 88200-B     3 88300-C   ✗  ← 사실 맞게 읽음
3 88300-C     4 88400-D   ✗
```
**결정.** no로 짝짓는다
- json 1000개에서 한 도면 안에 no가 겹치는 경우 0건 (part_no도 0건)

**함정.** no도 모델이 읽은 값이다
```
정답 13 → 출력 18 (오독)
  → 13은 "빠진 행", 18은 "생긴 행" → 오독 1개가 행 누락처럼 보이고 오류 2개로 셈
```
- 행 점수는 어차피 틀림 (no 칸이 틀림). 문제는 **원인 진단**
- 대응: no로 못 짝지은 행끼리 **품번이나 행 순서로 2차 짝짓기** → 맞으면 "글자 오류", 끝까지 안 맞으면 "행 누락/추가"

## 3. 원인 가르기
**결정.** 위 단계부터 차례로 정답 json과 비교
| 단계 | 비교 | 판정 |
|---|---|---|
| 표 찾기 | 행 수 vs `table_rows` 개수, 수량 열 수 vs `num_parents` | 다르면 표 찾기·칸 나누기 |
| 글자 나누기 | 칸의 묶음 수 vs 정답 글자 수 | 다르면 나누기 |
| 모델 | 개수는 같은데 글자 내용이 다름 | 모델 (`88100`→`88180`은 개수로 못 잡음) |
- 앞 단계 실수는 뒤로 번지므로, 앞 단계가 틀렸으면 뒤 단계 탓으로 세지 않는다
- 틀린 행마다 "표 / 나누기 / 모델" 꼬리표 → 단계별 개수로 고칠 곳의 우선순위
- header_style별, 페이지 크기별, 칸 종류별로 쪼개 보기

## 4. 자동 라벨링과의 차이
정답 출처(json)는 같지만 쓰는 방식이 다르다.
| | 자동 라벨링 (학습) | 평가 |
|---|---|---|
| 대상 | train PDF | test PDF |
| json 사용 | 칸 정답을 글자별로 쪼개 카드 뒷면에 | 최종 출력(행/칸)과 통째로 비교 |
| 개수 안 맞으면 | 칸을 **버림** | **틀린 걸로 셈** |
- 평가에서 버리면 어려운 칸을 빼고 채점해 점수가 부풀려진다. 실제 사용에선 못 버린다
- 글자 정확도(진단용)만 test에서 자동 라벨링 카드로 잰다. 주 점수(행)는 출력과 json을 직접 비교
