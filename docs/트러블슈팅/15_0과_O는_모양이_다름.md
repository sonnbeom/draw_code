# 15. "0과 O는 모양이 같다"는 잘못된 가정 → 선분 세로 변 길이로 100% 가름

> 5단계 OCR. 품번 0/O 형식 규칙([설계 19](../설계/19_OCR_전략.md), [OCR 21](../OCR/21_OCR_전략.md) 5절)의 전제를 바꿈

## 증상
- 펜 굵기 2로 바꾼 뒤 남은 오류의 대부분이 품번 0/O (0601~0820: `O→0` 36, `0→O` 17)
- 형식 규칙 "`-` 바로 뒤 + 다음이 알파벳이면 `O`, 나머지 `0`"이 json 통계상 약 1.7% 품번에서 구조적으로 틀림 (`-` 뒤 + 알파벳 앞인데 실제 `0` 55건 / 그 밖인데 실제 `O` 160건)

## 원인
- **"이 글꼴에서 0과 O는 선분 모양이 같다"는 가정을 확인 없이 써 옴** → 그림으로 못 가린다고 보고 통계 규칙으로 덮음
- 글자 사전(`bom/dictionary/glyph_dict.json`, 0001~0600)을 비교해 보니 모양이 다름 (글자 높이 = 1 기준, 폭은 둘 다 0.92)

| | 세로 변 길이 | 모서리 깎인 길이 | 사전 변형 / 등장 수 |
|---|---|---|---|
| `O` (알파벳) | **0.69** | 0.15 | 6가지 / 3716번, 서로 0.01 안 |
| `0` (숫자) | **0.54** | 0.23 | 3가지 / 18394번, 서로 0.01 안 |
- `O`와 `0` 사이만 일정하게 0.08 차이. 글자 32px로 그리면 약 2.6px → OCR은 사실상 가리지 못하고 아무거나 고름 (영어 모델은 `O` 쪽으로 기움)

## 해결 후보
| 후보 | 결과 |
|---|---|
| 형식 규칙 유지 (지금) | ✗ 약 1.7% 구조적으로 틀림 |
| 학습으로 OCR이 가리게 | △ 모양이 다르니 배울 수는 있음. 2.6px 차이라 될지는 돌려 봐야 앎 |
| **선분으로 판정** | ✓ 팔각형 덩어리(선분 8개, 폭 0.85~1.0, 높이 0.9~1.1, 양쪽 세로 변 길이 같음)의 세로 변 > 0.62면 `O`, 아니면 `0` |

선분 판정 측정 (scratchpad, OCR 없이 정답 json의 0/O 순서와 비교):
| 범위 | 0/O가 든 칸 | 0/O 글자 | 맞음 |
|---|---|---|---|
| 0001~0600 | 11077 | 24731 | **24731 (100%)** |
| 0601~0820 | 4288 | 9649 | **9649 (100%)** |
- 세로 변 길이는 0.53~0.54 / 0.69~0.70 두 묶음뿐, 중간값 없음
- 처음엔 팔각형 조건을 "선분 8개 + 폭·높이"만으로 했다가 다른 글자(세로 변 0.39) 432개가 섞임 → "양쪽 세로 변 길이가 같고 0.45~0.8" 조건을 더해 0개
- 세로 변 길이는 글자를 가로로 눌러도 안 변함 → 글자 사전이 실패한 긴 품명에서도 됨
- 테스트 도면 6개 중 4개도 0.54 / 0.69 두 묶음. **88300·88400은 팔각형이 안 잡힘** → 구현 때 확인

**결정 (2026-11-27). 0/O는 선분이 판정한다.**
- 역할: OCR = 줄 전체를 읽고 0/O 자리를 알려 줌 / 선분 = 그 자리마다 `0`인지 `O`인지 최종 판정 / 개수 비교 = OCR의 0/O 개수 ≠ 팔각형 개수면 바꾸지 않고 검수 표시
- 형식 규칙 `fix_part_no`는 필요 없어짐 (구현 후 측정으로 확인)
- 같은 구조를 `-`에도 씀: 선분으로 센 `-` 개수 = 정답 `-` 개수 (0001~0600 50466칸, 0601~0820 20218칸 모두 100%) → OCR 결과와 개수가 다르면 OCR이 놓친 것

## 교훈
- "모양이 같다"는 데이터에 대한 주장인데 확인 없이 설계 전제로 씀 → 규칙·문서·학습 계획이 모두 그 위에 쌓임. 이미 가진 데이터(글자 사전)로 몇 분이면 확인할 수 있었음
- OCR이 못 가리는 것 ≠ 그림에 정보가 없는 것. 사람 눈·OCR에 미묘한 차이도 선분 좌표에는 정확히 남아 있음 → **선분으로 확실히 아는 글자는 선분으로**
