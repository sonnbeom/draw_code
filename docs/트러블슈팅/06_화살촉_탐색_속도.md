# 06. 화살촉 찾기: 모든 선을 다 비교하면 28억 번 → 좌표 칸(격자 인덱스)으로 근처만 (2026-11-19)

> 관련: [04 화살촉 틈](04_화살촉_틈.md) (화살촉을 왜 찾는지), 코드 `bom/find_table/arrows.py`

## 배경: 무엇을 하려던 것인가
- 도면 PDF에서 하위 BOM 표를 찾으려면, 상위 부품에서 내려온 **연결선이 표 윗변에 닿는지** 봐야 한다
- 실제 도면은 연결선 끝에 **화살촉(작은 삼각형)**이 있어서, 선이 표보다 8.5 위에서 끊겨 있다
- 그래서 "이 삼각형이 화살촉인가?"를 판정하고, 화살촉이면 선 끝을 꼭짓점(표 윗변)까지 늘린다
- 판정하려면 **삼각형마다** "이 삼각형의 변에 끝이 닿는 선이 있는가?"를 찾아야 한다 ← 여기서 문제

## 증상 (예상된 문제, 짜기 전에 막음)
가장 단순하게 짜면 이중 for문이다.
```python
for tri in triangles:      # 삼각형마다
    for ln in lines:       # 도면의 모든 선을 다 보면서
        if 끝이_변에_닿나(ln, tri): ...
```
가장 큰 테스트 도면 88500 기준:

| 항목 | 개수 |
|---|---|
| 선 | 약 65만 개 |
| 선 3개짜리 삼각형 | 약 4,300개 |
| 비교 횟수 | 4,300 × 65만 ≈ **28억 번** |

Python에서 28억 번 반복하면 도면 하나에 수십 분 단위가 걸린다 (직접 재지는 않음, 추정). 도면을 여러 장 돌려야 하니 쓸 수 없다.

## 원인
- 삼각형 변에 닿을 수 있는 선은 **그 삼각형 바로 옆에 있는 선**뿐이다 (닿음 허용 오차 0.5pt)
- 그런데 이중 for문은 도면 반대편 수만 pt 떨어진 선까지 전부 확인한다 → 비교의 거의 전부가 낭비
- 즉 문제는 "계산이 어렵다"가 아니라 **"볼 필요 없는 걸 다 본다"**

## 해결 후보
| 후보 | 방법 | 장점 | 단점 |
|---|---|---|---|
| A. 이중 for문 | 삼각형 × 전체 선 | 코드 제일 쉬움 | 28억 번, 못 씀 |
| B. 좌표 정렬 + 이진 탐색 | 선을 x로 정렬, x가 가까운 것만 | 정렬 한 번 | x만 가깝고 y는 먼 선이 많이 섞임 (세로로 긴 도면). 2차원에 약함 |
| C. 공간 트리 (KD-tree, R-tree) | 라이브러리로 범위 검색 | 범용·정확 | 새 패키지(scipy 등) 필요, 동작 원리를 따로 익혀야 함 |
| **D. 격자 인덱스 (공간 해싱)** | 도면을 일정 크기 칸으로 나누고 칸마다 끝점 목록을 미리 만든다 | 표준 라이브러리(dict)만으로 됨, 원리가 단순 | 칸 크기를 정해야 함, 칸 경계 처리 필요 |

## 결정: D. 격자 인덱스
"근처만 본다"만 하면 되고, 찾는 범위(삼각형 변 주변)가 늘 작아서 가장 단순한 D로 충분하다.

### 동작 원리 (3단계)

**① 칸 번호 매기기**: 좌표를 칸 크기(10pt)로 나눈 몫 (`_cell`)
```
(123.4, 57.8) → (12, 5)
(128.9, 51.0) → (12, 5)   ← 가까운 점은 같은 칸
(305.0, 57.8) → (30, 5)   ← 먼 점은 다른 칸
```

**② 미리 색인 만들기**: 선 전체를 **딱 한 번** 훑으며, 선의 두 끝점을 각자 칸에 넣는다 (`_index_endpoints`)
```
index = {
  (12, 5): [(선 7번, 1번 끝), (선 42번, 2번 끝)],
  (30, 5): [(선 99번, 1번 끝)],
  ...
}
```
- Java로는 `Map<Cell, List<EndRef>>`. DB 테이블에 인덱스를 거는 것과 같은 발상이다. 매번 전체 스캔하지 않고 키(칸 번호)로 바로 찾아간다
- 끝점만 넣는 이유: 찾는 조건이 "선의 **끝**이 변에 닿는가"라서 선의 몸통은 필요 없다

**③ 삼각형 변 근처 칸만 꺼내 보기**
```
밑변 (120, 50) ~ (128, 52)  →  칸 (12, 5)
이웃 칸까지 ±1  →  3 × 3 = 9칸만 검사

 (11,4) (12,4) (13,4)
 (11,5) (12,5) (13,5)    ← 이 9칸에 든 끝점만 비교
 (11,6) (12,6) (13,6)
```
- 밑변이 칸 경계에 걸치면 범위가 늘어난다: 밑변이 걸친 칸 `min`~`max`에 ±1 (예: 밑변 (128, 52)~(131, 52) → x 11~14 × y 4~6 = 12칸)
- **왜 이웃 칸까지 보나 (칸 경계 문제):** 끝점이 변에서 0.5 이내라 "닿는다"인데 칸 경계를 넘어 옆 칸에 들어갈 수 있다. 예: 변이 y=49.9(칸 4), 선 끝이 y=50.2(칸 5). 그래서 한 칸씩 여유를 둔다

### 칸은 거르기만, 판정은 정확한 계산
| 단계 | 하는 일 | 코드 |
|---|---|---|
| ① 거르기 (칸) | 밑변 근처 칸에 **끝점**이 있는 선만 후보로 꺼냄 | `merge_arrows` 칸 반복 |
| ② 판정 (계산) | 후보 끝점과 밑변의 실제 거리 ≤ 0.5, 위치 30~70%, 방향 | `_position_on_side` 등 |

예: 밑변 (128, 52)~(131, 52)
| 후보 끝점 | ② 결과 |
|---|---|
| (129.5, 52.3) | 거리 0.3, 위치 50% → ✓ |
| (128.2, 52.1) | 위치 7% → ✗ (꼭짓점 근처) |
| (135.0, 58.0) | 근처 칸이지만 거리 6.0 → ✗ |
| (500.0, 52.0) | 칸 밖이라 꺼내지도 않음 |

- 근처 칸에 있어도 안 닿으면 ②에서 걸러지므로, **칸 때문에 판정이 틀리는 일은 없다** (판정 계산은 이중 for문 때와 같음)
- **놓치는 경우도 없다**: 닿는 끝점은 반드시 "밑변을 0.5 넓힌 네모" 안에 있고, 칸 크기 10 ≥ 0.5라서 그 네모는 밑변 칸 ±1 안에 들어간다. 즉 조건 **칸 크기 ≥ 허용 오차**가 누락 없음을 보장한다
- 끝점만 색인하는 이유: 조건이 "선의 **끝**이 변에 닿음"이라 변을 가로질러 지나가는 선은 대상이 아님

### 칸 크기 10의 근거
- 필수 조건: 칸 크기 ≥ 허용 오차 0.5 (위 누락 없음 보장)
- 트레이드오프: 너무 작으면 밑변 하나가 여러 칸에 걸쳐 꺼낼 칸이 늘고, 너무 크면 한 칸에 끝점이 몰려 다시 전수 비교에 가까워짐
- 10은 화살촉 밑변(약 2.8)이 1~2칸에 드는 크기로 고른 값. **다른 크기(5·20 등)와 비교 측정은 안 함**
- 칸 개수는 도면 크기에 따름 (A3 약 120×85, 가장 큰 11905×2383.94는 약 1191×239). `defaultdict`라 끝점이 있는 칸만 메모리에 생김

### 비용 비교
| | 이중 for문 | 격자 인덱스 |
|---|---|---|
| 색인 만들기 | 없음 | 선 65만 개 1번 훑기 |
| 삼각형 하나당 비교 | 65만 번 | 9칸 안의 끝점만 (근처 선 수, 개수는 따로 안 잼) |
| 88500 전체 | ≈ 28억 번 (수십 분 추정) | **3.4초** |

## 결과
- 88500 화살촉 합치기 3.4초 (선 65만 개 도면)
- 결과는 이중 for문과 같다: 근처가 아닌 선은 애초에 닿을 수 없으니 빼도 놓치는 것이 없음

## 교훈
- 느린 원인을 "계산량"이 아니라 **"안 봐도 되는 걸 보는가"**로 먼저 따진다
- 위치 데이터에서 "근처 찾기"는 좌표를 칸으로 묶은 해시 맵 하나로 크게 줄일 수 있다 (O(삼각형 × 선) → O(선 + 삼각형 × 근처))
- 칸으로 나누면 **경계에 걸친 경우**를 꼭 따로 생각한다 (이웃 칸 ±1)
- 같은 문제가 남은 곳: `table_candidates.py`의 `group_lines`도 이중 for문 (닿는 선끼리 묶기). 글자 획을 지운 뒤라 선이 적어 지금은 버티지만, 88500 17.9초의 대부분이 여기. 느려지면 같은 격자 인덱스로 바꾼다 (TODO)
