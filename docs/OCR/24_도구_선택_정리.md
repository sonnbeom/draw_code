# OCR 도구 선택: 프로그램·엔진·모델과 그 근거

> 어떤 OCR을 왜 골랐고 무엇을 왜 뺐는지, 비교 측정 기록. 결론과 이유만 읽으려면 [25](25_RapidOCR_선택_이유.md). 처음 결정은 [설계 19](../설계/19_OCR_전략.md) 6절, 요약은 [20](20_OCR_흐름_이해.md)

## 1. 세 층
| 층 | 고른 것 | 역할 | Java 비유 |
|---|---|---|---|
| 프로그램 | RapidOCR (`rapidocr_onnxruntime`) | 그림 전처리 → 모델 실행 → 글자로 | 라이브러리 |
| 실행 엔진 | onnxruntime | onnx 모델 파일 계산 (실행만, 학습 못 함) | JRE |
| 모델 | PP-OCRv4 영어 인식 mobile (`models/en_PP-OCRv4_rec_mobile.onnx`, 7.6MB) | 줄 그림 → 글자 확률 | 실행할 `.jar` |
| 학습 도구 (학습 때만) | PaddlePaddle + PaddleOCR 저장소 | 모델 미세조정 → onnx로 변환 | JDK + 빌드 도구 |
- PP-OCR은 Baidu가 자기 학습 엔진 PaddlePaddle로 만든 모델. RapidOCR은 그걸 onnx로 바꿔 가볍게 돌리는 포장 → 실행에는 PaddlePaddle이 필요 없고, 학습할 때만 원래 도구로 돌아감 ([23](23_학습_계획.md))

## 2. 기준: 필수 조건과 가르는 조건
OCR은 검출(글자 위치 찾기) + 인식(줄 그림 → 글자) 두 단계. 우리는 위치를 선 좌표로 이미 알아서 **인식만** 필요
| 구분 | 기준 | 역할 |
|---|---|---|
| 필수 조건 | 인식만 따로 쓸 수 있음 / PC 안에서 실행 (회사 도면이 밖으로 안 나감) | 못 맞추면 탈락. **RapidOCR만의 장점은 아님** (Tesseract PSM 7, EasyOCR, PaddleOCR, TrOCR도 됨) |
| 가르는 조건 | 우리 글씨 정확도 / 속도 / 학습 경로 / 배포 | 남은 후보 중 하나를 고름 |

## 3. 후보와 결과
| 후보 | 기반 | 결과 | 이유 |
|---|---|---|---|
| **RapidOCR** | onnxruntime | **채택** | 아래 4절 |
| Tesseract 5 | 별도 프로그램 | **비교 측정** (5절) | RapidOCR보다 못하다는 측정 근거가 없음 |
| PaddleOCR | PaddlePaddle | 실행용 제외, 학습용 | RapidOCR과 같은 모델인데 설치가 가장 무거움 |
| EasyOCR | PyTorch | 제외 | 설치 수백 MB, CPU에서 느린 편 |
| 클라우드 (Google·Azure·AWS·CLOVA) | 외부 서버 | 제외 | 필수 조건 위반 (도면 외부 전송) |
| docTR, TrOCR, MMOCR, Windows 내장 OCR | PyTorch 등 | 검토 안 함 | 나중 후보 (TrOCR은 크고 CPU에서 느린 편, Windows 내장은 학습 불가 — 일반론) |
| 직접 만든 인식 모델 | PyTorch 등 | 보류 | 99.8%에서 출발 못 함 |

## 4. RapidOCR 근거와 강도
| 근거 | 내용 | 강도 |
|---|---|---|
| 정확도 | 품명 99.8% (0601~0820, 2761칸) | 확인, **다른 엔진과 비교 없음** |
| 모델 교체 | 파일 경로만 바꿔 중국어+영어 → 영어 모델 비교: 품명 느슨 69.7% → 76.3%, 수량 70.3% → 100% (0601~0650) | 확인 |
| 속도 | 프로그램 안에서 함수 호출, 모델은 한 번만 올림. 칸당 18ms | RapidOCR만 확인. Tesseract(`pytesseract`)는 호출마다 별도 프로그램 실행 → 비용 크기는 안 잼 |
| 학습 경로 | `en_PP-OCRv4_mobile_rec.yml` 설정 + 원본 가중치 191MB 공개 (2026-11-27 확인) | 확인. Tesseract도 학습 가능, Windows에서 번거롭다는 건 일반론 |
| 배포 | `pyproject.toml` + `uv.lock`에 버전 고정 → 어느 PC든 같은 결과, 별도 프로그램·PATH 없음, 오프라인. 설치 16MB + onnxruntime 49MB + 모델 7.6MB | 보조 근거 (관리자 권한 정책은 확인 필요) |
| 낯선 글꼴·눌린 글씨 | PP-OCR은 다양한 글꼴로 학습돼 강하다고 알려짐 | 일반론 |

**결론.** 조건으로는 RapidOCR이 맞지만 **Tesseract보다 낫다는 측정 근거는 없음** → 둘 다 같은 줄 그림으로 재서 비교

## 5. 결정: RapidOCR vs Tesseract 비교 측정 (학습 전)
| 시점 | 장점 | 단점 |
|---|---|---|
| **학습 전** | 원래 모델끼리 공정 비교. 이미 있는 측정 틀(`compare_readers`: 열별 정답률·CER·혼동 목록)에 엔진만 바꿈 | 학습이 조금 늦어짐 |
| 학습 후 | 학습 먼저 | 학습한 RapidOCR vs 원래 Tesseract → 공정하지 않음 |
- **결정 (2026-11-27). 학습 전에 비교.** 결과가 어느 쪽이든 쓸모 있음: RapidOCR 우세 → "측정해서 고름", 비슷하거나 Tesseract 우세 → 다른 실수를 하는 투표자 후보 ([22](22_합의와_점수.md) 3절 B)
- 조건: 같은 줄 그림 (글자 32px, 굵기 3), 0601~0820, 같은 형식 규칙, 취소·검수 칸 제외

### 결과 (2026-11-27, Tesseract 5.4.0 UB Mannheim 배포판, `eng`, `--psm 7 --oem 1`)
방법: `compare_readers` 줄 모드에서 `Ocr`만 Tesseract로 바꿈 (scratchpad 실험). 같은 줄 그림 3644장(서로 다른 것)을 모아 한 번 실행으로 읽고, 같은 형식 규칙·CER·혼동 목록으로 측정

| 열 | RapidOCR 영어 | Tesseract 기본 | Tesseract 허용 글자 제한 |
|---|---|---|---|
| I/NO | 100% / CER 0% | 78.9% / 31.0% | 77.3% / 20.0% |
| 품번 (느슨) | 100% / CER 0.17% | 0.4% / 14.9% | 68.7% / 4.6% |
| 품명 | **99.8% / CER 0.007%** | 20.7% / 3.9% | 88.9% / 0.46% |
| 수량 | 100% / CER 0% | 72.4% / 60.5% | 74.2% / 31.4% |
| **전체 CER** | **0.049%** | 13.4% | 5.3% |
| 속도 | 칸당 18ms (프로그램 안) | 한 번에 몰아 읽기 줄당 8ms / 줄마다 실행 줄당 85ms | 〃 |

- Tesseract 기본: `-`를 긴 줄표 `—`로 읽음 (품번 2391, 품명 1849번) → 허용 글자 제한으로 사라짐
- 허용 글자 제한은 공백도 목록에 넣어야 함 (빠뜨리면 품명 띄어쓰기 7001개가 사라짐)
- Tesseract 남은 혼동: 한 글자 칸 `2`→`)`·`]`, `4`→`A` / 품번 글자 끼어듦 (`(없음)→0` 387, `8→S` 114) / 품명 `3→8` 55, `[`→`(` 50, `(` 끼어듦 93
- **`D`/`O`는 Tesseract가 안 헷갈림**: Tesseract 결과에 `OLX` 0번, `DLX` 146번 (서로 다른 줄 그림 기준). RapidOCR이 틀리는 곳에서 맞음 → **서로 다른 실수**
- 주의: 그림 설정(32px·굵기 3)은 RapidOCR에 맞춰 고른 값이라 Tesseract에 불리할 수 있음 (Tesseract에 맞춘 크기는 안 재 봄)
- 속도: 인식 자체는 Tesseract가 빠름 (몰아 읽기 8ms). 줄마다 프로그램을 띄우면 85ms로 느려짐 → 호출 방식 비용이 실제로 큼 (4절 속도 근거 확인)

### 공정 비교: 같은 그림 설정 묶음을 두 엔진에 (2026-11-27)
32px·굵기 3이 RapidOCR에 맞춘 값이라, 글자 높이·펜 굵기를 바꿔 둘 다 잼 (Tesseract는 허용 글자 제한 상태). 셀 = 품명 정확 / 전체 CER
| 그림 설정 | RapidOCR | Tesseract |
|---|---|---|
| 24px 굵기 3 | 90.3% / 0.316% | 85.9% / **3.888%** (Tesseract 전체 최고) |
| 32px 굵기 2 | **100%** / 0.047% | 86.6% / 7.898% |
| 32px 굵기 3 (지금) | 99.8% / 0.049% | 88.9% / 5.295% |
| 32px 굵기 4 | **100%** / 0.049% | **94.1%** / 5.803% (Tesseract 품명 최고) |
| 40px 굵기 3 | 99.9% / 0.052% | 86.3% / 5.202% |
| 48px 굵기 3 | **100%** / **0.046%** | 78.2% / 9.567% |
| Tesseract 단어 사전 끔 (32px 굵기 3) | — | 88.9% / 5.295% (변화 0, 설정이 실제로 먹혔는지는 확인 못 함) |
- Tesseract는 설정마다 강한 열이 다름 (24px: 수량 90.9%, 굵기 4: 품명 94.1%·품번 73.3%) → 어느 설정이든 전체 CER 3.9% 이상
- RapidOCR은 24px만 약하고 나머지는 전부 CER 0.05% 안팎 → **설정에 덜 민감**
- 결론: **Tesseract에 가장 유리한 설정끼리 비교해도 RapidOCR이 크게 앞섬** (가장 좋은 Tesseract 3.9% vs RapidOCR 0.05%)

### 여백 (PAD, 지금 8px)
- Tesseract 한 글자 모드(`--psm 10`)는 효과 0 (그림 한 장씩 넣어도 psm 7과 같은 결과). 단어 사전 끄기도 0
- 깨끗한 `2` 그림(48×43px)을 Tesseract가 `y=)`로 읽음 → 흰 여백만 20px로 늘리자 `2` → 여백을 바꿔 전체 측정

| 여백 | RapidOCR 품명 / 전체 CER | Tesseract I/NO · 품번(느슨) · 품명 · 수량 / 전체 CER |
|---|---|---|
| 8px (지금) | **99.8% / 0.049%** | 77.3 · 68.7 · 88.9 · 74.2% / 5.30% |
| 16px | 76.2% / 0.634% (`,→.` 639, `D→O` 56) | 88.8 · 72.8 · 88.3 · **100%** / **1.66%** (Tesseract 최고) |
| 24px | — | 87.8 · 73.6 · 87.6 · 96.1% / 1.90% |
- **엔진마다 맞는 그림이 다름**
  - Tesseract: 글자 위치·크기를 규칙으로 먼저 찾고 읽음 → 둘레 흰 공간이 좁으면 위치 찾기부터 틀림 (`2` → `y=)`, 한 글자를 조각으로 나눈 것으로 추정)
  - RapidOCR: 그림을 높이 48로 맞춤 → 여백 16이면 그림 높이 64가 48로 줄어 글자가 실제 24px꼴 → 24px 때와 같은 오류 (`,→.`, `D→O`)
- 각자 가장 좋은 설정끼리: RapidOCR 0.046~0.049% vs Tesseract 1.66% → **약 35배**. 여백을 맞춰도 남는 Tesseract 오류: 품번 글자 끼어듦 `(없음)→0` 405 · `5→S`, 품명 `[→(` 125 · `3→S` 85
- 여백 16에서는 Tesseract도 `D→0` 22, `D→O` 9 → "Tesseract는 D/O를 안 헷갈림"은 여백 8 + 허용 글자 제한 설정에서만 맞음 (앙상블 검토 때 설정째로 다시 확인)
