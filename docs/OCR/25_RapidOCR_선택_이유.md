# 왜 RapidOCR인가: 프로젝트 특성 × 엔진 특성

> 결론과 이유를 한 장으로. 측정 숫자·실험 방법은 [24](24_도구_선택_정리.md), 처음 결정은 [설계 19](../설계/19_OCR_전략.md) 6절
> 표시: **[측정]** 우리가 직접 잰 것 / **[일반론]** 알려진 사실이지만 우리가 증명하지 않은 것

## 1. 결론
- **OCR 프로그램 RapidOCR + 실행 엔진 onnxruntime + 모델 PP-OCRv4 영어 인식(mobile)**
- 이유 한 줄: 우리 도면의 글자(낯선 CAD 선 획 글꼴, 가로로 눌린 품명, 단어가 아닌 품번, 한 글자 칸)를 **학습 없이도 거의 다 읽고**, 회사 PC 안에서 가볍게 돌며, 더 다듬을 학습 경로도 열려 있다
- Tesseract와 각자 가장 좋은 그림 설정으로 비교해 전체 CER **0.05% vs 1.66% (약 35배)** [측정]

## 2. 프로젝트 특성 (OCR이 받는 조건)
| 특성 | 내용 | OCR에 주는 요구 |
|---|---|---|
| 위치는 이미 앎 | 표·칸·줄을 PDF 선 좌표로 정확히 찾음 | 글자 위치 찾기(검출)는 필요 없음, **인식만** |
| 그림은 우리가 그림 | 선분 → 줄 그림을 직접 그림 (글자 높이·펜 굵기·여백을 우리가 정함) | 입력 준비를 엔진에 맞출 수 있음 |
| 낯선 글꼴 | CAD 스트로크 글꼴: 굵기가 일정한 선 획 (일반 인쇄 글꼴처럼 속이 채워진 글자가 아님) | 처음 보는 글자 모양에 강해야 함 |
| 열마다 문자열 성질이 다름 | I/NO·수량: 한 글자 (`2`, `4`, `-`) / 품번: 단어가 아닌 문자열 (`88210-0S52O`) / 품명: 가로로 눌린 긴 영어 (`HEIGHT ADJUSTER LINK-FRT, LH (DLX)`) | 한 글자, 단어 아닌 줄, 눌린 글씨 모두 |
| 글자 종류가 좁음 | json 1000개에 대문자·숫자·기호만, 소문자 0개 | 엉뚱한 글자(소문자·한자·`—`)를 안 내야 함 |
| 회사 도면 | 외부로 내보내면 안 됨 | **PC 안에서 실행** (클라우드 불가) |
| 실행 환경 | Windows, GPU 없음, 도면 한 장씩 처리 | CPU에서 빠름, 설치가 단순 |
| 정답이 있음 | 샘플 1000개의 json 정답 | 엔진끼리 숫자로 비교 가능 |
| 학습도 목표 | 구현과 학습(ML 과정 배우기)이 모두 목표 | 미세조정 경로가 있어야 함 |

## 3. 엔진 특성
| | RapidOCR (PP-OCR 모델) | Tesseract 5 |
|---|---|---|
| 출신 | 2020년 이후 Baidu PP-OCR을 onnx로 포장 | 1980년대 HP → Google, 스캔 문서용 |
| 읽는 방식 | 줄 그림을 **높이 48로 맞춰 통째로 신경망**에 넣음 | ① 규칙으로 글자 위치·크기 찾기 → ② 신경망(LSTM)으로 읽기 |
| 배운 글자 | 사진·간판·문서 등 다양한 모양 [일반론] | 주로 일반 인쇄 글꼴 문장 [일반론] |
| 글자 목록 | 영어 모델 ASCII 95자 (`—`·소문자 대신 대문자 같은 문제 구조적으로 적음) [측정: `models/en_dict.txt`] | 인쇄 기호까지 넓음 → 허용 글자 제한 옵션 있음 |
| 입력 준비 | 지금 그림 설정(32px·여백 8 = 높이 48)에 맞음. 여백을 늘리면 오히려 나빠짐 [측정] | **둘레 흰 공간이 좁으면 ①부터 틀림**. 여백 16px에서 좋아짐 [측정] |
| 실행 | Python 라이브러리, 프로그램 안에서 함수 호출 | 별도 실행 파일. 줄마다 띄우면 85ms, 몰아 읽으면 8ms [측정] |
| 설치·배포 | `uv add` (16MB + onnxruntime 49MB + 모델 7.6MB), `uv.lock`에 버전 고정 [측정] | Windows 설치 프로그램 따로, 쓸 PC마다 |
| 학습 | PaddleOCR로 학습 → onnx 변환. 설정 파일·원본 가중치 공개 [확인] | tesstrain, Windows에서 번거로움 [일반론] |

다른 후보: EasyOCR (PyTorch, 무겁고 느림 → 제외), PaddleOCR (같은 모델인데 무거움 → 학습 도구로만), 클라우드 OCR (외부 전송 → 제외), docTR·TrOCR·MMOCR (검토 안 함). 자세한 표는 [24](24_도구_선택_정리.md) 3절

## 4. 특성 맞추기: 프로젝트 요구 → 어느 엔진이 맞나
| 프로젝트 요구 | RapidOCR | Tesseract | 근거 |
|---|---|---|---|
| 인식만 따로 | ✓ (`use_det=False`) | ✓ (`--psm 7`) | 둘 다 됨 → **가르는 기준 아님** |
| PC 안에서 실행 | ✓ | ✓ | 둘 다 됨 → 가르는 기준 아님 |
| 한 글자 칸 | I/NO·수량 100% | 여백을 맞춰도 I/NO 88.8% | [측정] |
| 단어가 아닌 품번 | 느슨 100% | 약 73% (없는 `0` 끼어듦 405번, `5→S`) | [측정] |
| 눌린 긴 품명 + 낯선 글꼴 | 99.8% (최선 설정 100%) | 약 88% (`[→(` 125번, `3→S` 85번) | [측정] |
| 엉뚱한 글자 안 냄 | 글자 목록이 원래 좁음 | 기본 설정은 `-`를 `—`로 수천 번 → 허용 글자 제한 필요 | [측정] |
| 입력 준비에 덜 민감 | 6개 그림 설정 중 5개가 CER 0.05% 안팎 | 설정마다 강한 열이 다름, 여백에 크게 흔들림 | [측정] |
| 빠름 | 칸당 18ms | 몰아 읽으면 빠름, 줄마다 실행은 느림 | [측정] |
| 배포 단순 | ✓ | 별도 설치 | 구조상 사실 |
| 학습 경로 | ✓ 출발점 99.8% | 가능, 출발점 약 88%·고칠 오류 종류 많음 | [확인] + [일반론] |

## 5. 왜 이런 차이가 나는가 (해석)
1. **입력 준비 차이 (고칠 수 있었음)**: Tesseract는 위치를 규칙으로 먼저 찾아서 여백이 좁으면 틀림 (`2` → `y=)`). 여백 16px로 맞추자 CER 5.3% → 1.66% [측정]. 이건 Tesseract의 한계가 아니라 "입력을 자기 방식에 맞춰 줘야 한다"는 특성
2. **읽는 능력 차이 (고칠 수 없음)**: 여백을 맞춰도 품번·품명 오류가 남음. 낯선 선 획 글꼴, 눌린 글자, 단어가 아닌 문자열은 **도면 자체의 성질**이라 그림 설정으로 못 없앰. 다양한 모양을 배운 PP-OCR이 유리 [일반론으로 해석, 오류 종류는 측정]
3. **엔진마다 맞는 그림이 다름**: 같은 "여백 16"이 Tesseract는 좋아지고 RapidOCR은 나빠짐 (그림 높이 64 → 48로 줄어 글자가 24px꼴, 쉼표 꼬리·`D` 직선이 흐려짐) [측정]. 그래서 공정 비교는 **각자 가장 좋은 설정끼리**

## 6. 학습 관점
- 둘 다 학습으로 나아질 수 있음. 하지만 RapidOCR은 **학습 없이도** 남은 오류가 `D→O` 5칸과 0/O(선분 판정 몫, [트러블슈팅 15](../트러블슈팅/15_0과_O는_모양이_다름.md))뿐 → 학습 부담이 훨씬 작음
- 그래도 RapidOCR을 학습하는 이유: `D`가 `D`/`O` 경계선 위에 있어 그림을 조금만 바꿔도 판정이 바뀜 (새 도면에서 흔들릴 수 있음) + 학습 과정을 배우는 것이 목표 ([23](23_학습_계획.md))
- Tesseract는 버리지 않음: 실수하는 곳이 달라 앙상블 투표자 후보 ([22](22_합의와_점수.md) 3절 B, 설정째로 다시 확인)

## 7. 한계 (솔직하게)
- 그림 설정·떨어진 `-` 처리·줄 잇기 규칙은 RapidOCR 결과를 보며 만듦. 그림 설정은 두 엔진 모두 바꿔 봤지만, 규칙은 Tesseract에 맞춰 바꿔 보지 않음
- 비교는 0601~0820(측정용 도면)에서 함. 엔진 선택은 차이가 커서 뒤집히기 어렵지만, **그림 설정을 고르는 데 이 숫자를 쓰면 안 됨** (0001~0600에서 확인 필요)
- docTR·TrOCR·MMOCR는 비교 안 함
- "배운 글자가 다양하다"는 학습 데이터에 대한 일반론

## 8. 면접용 정리
> "위치는 PDF 선 좌표로 이미 알아서 OCR은 **인식만** 필요했고, 회사 도면이라 **로컬 실행**이어야 했습니다. 이 두 조건은 Tesseract도 만족해서, 같은 줄 그림으로 직접 비교했습니다. 처음엔 Tesseract가 5.3%였는데 **여백이 원인**인 걸 찾아 맞춰 주니 1.7%까지 내려갔습니다. 그래도 **낯선 CAD 글꼴, 눌린 품명, 단어가 아닌 품번**에서 오류가 남아 RapidOCR(0.05%)과 약 35배 차이였습니다. 그림 준비가 아니라 우리 데이터 성질에 대한 엔진 차이라서 RapidOCR을 골랐고, 학습 없이도 잘 읽으니 학습 부담도 작았습니다. Tesseract는 실수하는 곳이 달라 앙상블 후보로 남겼습니다."
