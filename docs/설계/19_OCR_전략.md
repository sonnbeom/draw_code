# 19. OCR 전략: 읽는 단위·입력·사전과 비교

> 5단계. 앞 문서: [02](02_PDF구조와_OCR.md) 문제 3 (글자 읽기 = OCR), [15](15_전체_파이프라인.md) ⑥

## 문제 정의
- 4-1·4-2에서 만든 **글자 사전**이 이미 숫자·품번을 읽는다 (샘플 0601~0820)

  | 칸 | 사전 결과 |
  |---|---|
  | 수량 | 11935/11935 |
  | 품번 | 2761/2761 (0/O만 구분 못 함) |
  | 리비전 숫자 | 817/818 |
  | 품명 | 1138/2379 (긴 이름은 글자를 가로로 눌러 써서 안 맞음) |
- 정할 것: OCR을 어디에 쓸지, 한 번에 무엇을 읽힐지(단위), 입력 그림을 어떻게 만들지

## 1. OCR을 어디에 쓰나
| 후보 | 장점 | 단점 |
|---|---|---|
| 모든 칸 OCR | 읽는 방법이 한 가지 | 사전이 100% 맞히는 칸까지 OCR 오류 위험 |
| 사전이 못 읽는 칸만 OCR (품명·머리글·검수 칸) | 숫자·품번은 검증된 사전 | 읽는 방법이 두 가지 |

**결정.** 먼저 **모든 칸을 OCR로 읽고 사전과 같은 줄에서 비교**한 뒤 정한다. 모듈은 따로 만든다.
| 파일 | 하는 일 |
|---|---|
| `bom/read_text/cell_image.py` | 줄 그림 만들기 (취소선·삼각형·연결선을 뺀 획만) |
| `bom/read_text/ocr.py` | OCR 엔진 감싸기: 그림 → (글자, 자신감). 엔진을 바꿔도 여기만 고침 |
| `bom/glyph_reader.py` | 사전 읽기 (`glyphs.match_glyphs`를 줄 단위로) |
| `explore/measure_ocr/compare_readers.py` | 샘플 0601~0820: 열별 정확도 OCR vs 사전 = json, 틀린 예시 |

## 2. 읽는 단위
예: 88500 품번 칸 `88600-NR480`
| 후보 | 장점 | 단점 |
|---|---|---|
| A. 글자 하나 | 글자별 결과 | 글자 나누기가 어려움 (`22`는 끝점 공유, 긴 품명은 겹침, [06](06_취소선.md)). 앞뒤 맥락이 없어 OCR이 약함. 호출 가장 많음 |
| **B. 칸 안의 한 줄** | 위치는 선 좌표로 이미 앎 → OCR은 읽기만. json이 칸 단위라 바로 비교. 사전·취소 판정(4-1)과 같은 단위 | 호출 수 = 줄 수 (여러 장을 묶어 보내 완화) |
| C. 표 전체 | 호출 1번 | OCR이 위치를 찾고 칸을 다시 배정해야 함. 이웃 칸 글자를 붙여 읽을 수 있음. 큰 표는 줄이면 글자가 작아짐 |
| D. 행 하나 | 중간 | 행 안에서 칸을 다시 나눠야 함. C의 단점이 작게 남고 얻는 게 없음 |

**결정 (처음). B (칸 안의 한 줄).** → 아래 "여러 줄 칸"에서 **칸 모드를 먼저 재 보는 것으로 바꿈**
- 위치(칸, 몇 번째 줄)는 선 좌표로 안다: `strokes_by_cell` → `split_text_lines`, 상위는 `parent_cells`, 리비전은 삼각형 안쪽
- OCR의 글자 위치 찾기(검출)는 쓰지 않고 인식만 쓴다
- 칸 값 조립: 한 줄 칸 = 그 줄, 두 줄 품명 = 위 + 공백 + 아래 (json 형식은 구현 때 확인)
- 구현 때 확인: 긴 품명이 칸 경계를 넘어 옆 칸에 그려진 경우가 있는지

**취소하고 새로 쓴 칸.** 취소 여부는 OCR이 아니라 4-1 판정(`rules.mark_cells`의 줄별 정상/취소/검수)이 정한다. OCR은 글자만 읽는다.
| 배치 | 처리 |
|---|---|
| 옛 값 위, 새 값 아래 (22000 수량 `2` 취소 + `1`, 상위 교체) | 줄 나누기가 이미 둘로 가름 → 줄마다 상태가 붙음 → 정상 줄 = 칸 값 |
| 같은 줄에 나란히 | 아직 못 봄. 나오면 4-1 끼워 맞추기의 글자 위치로 취소 조각 / 정상 조각을 나눠 그림 |
| 취소만 있음 | 칸 값 = 빈칸, 상태 = 취소 (행 전체면 json `is_deleted`와 비교) |
| 검수 | OCR 결과를 넣고 검수 표시 유지 |
- 그림에서 취소선은 뺀다 (`CellMark.strikes`). 남기면 `2`가 `Z`·`-2`로 읽힐 수 있음
- 취소된 줄도 OCR로 읽어 "이전 값"으로 남긴다 (검수 때 무엇 → 무엇인지 보임)
- 구현 때 확인: 바뀐 칸을 json이 어떻게 적는지 (새 값만인지)

### 여러 줄 칸: 줄은 누가 나누나
줄 그림을 만들어 보니 샘플 두 줄 품명이 한 줄로 붙어 나옴 (0601~0700에서 412칸). 윗줄 `,` `(` `)`가 아랫줄 높이까지 내려와 `split_text_lines`가 찾는 틈이 없어짐
```
 LOCATION PIN ASSY (SAB,
VENT)
```
인식 모델만 쓰면 한 줄씩만 읽는다. 검출까지 켜면 RapidOCR이 여러 줄을 스스로 나눈다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 줄 모드: 선 좌표로 줄 나누기 고침 (높이별 획 수의 골짜기에서 자름) | 줄 번호 = 4-1 판정, 빠름, 한 글자 칸도 그림 생김 | 줄 나누기 수정 + 4-1·4-2 재확인 |
| **칸 모드: 칸 그림 → 검출 + 인식** | 우리 코드 수정 없음 | 4-1 줄과 OCR 줄 상자를 y로 짝지어야 함. 검출이 작은 글자를 놓칠 수 있음. 느림 |

**결정. 칸 모드를 먼저 재고, 부족하면 줄 모드.**
1. 칸 모드로 샘플 0601~0820 열별 정답률 측정 (학습 전 기본 모델)
2. 부족하면 줄 모드로. 칸 단위로는 "OCR이 찾은 줄 수 ≠ 우리가 센 줄 수"인 칸만 줄 모드로 다시 읽는 절충도 가능
3. 그래도 틀리는 유형을 보고 미세조정 여부 결정 (아래 5)
- 취소된 줄이 있는 칸: 칸 그림에서 취소선은 빼고, OCR 줄의 가운데 y ↔ 우리 줄의 가운데 y(`CellImage.line_ys`)로 4-1 판정과 짝지음
- 첫 시도 (case_0601·88500·22000 몇 칸, [트러블슈팅 10](../트러블슈팅/10_OCR_검출이_칸을_키움.md) 고친 뒤)
  | 칸 | 결과 |
  |---|---|
  | 품번 `88114-TQ200`, 88500 `88100-NX560` | 맞음 (자신감 0.98, 0.89) |
  | 두 줄 품명 `LOCATION PIN ASSY (SAB, VENT)` | 두 줄 찾음, 첫 글자 `LO` → `Q` |
  | 머리글 `PART NAME` | `PART`·`NAME` 두 조각 (공백으로 이어 붙임) |
  | 한 글자 칸 (`-`, `1`) | 못 찾음 → 사전이 맡음 |
  | 88500 세 줄 품명 (눌러 쓰고 줄 간격 좁음) | 못 찾음 |

### 떨어진 `-`: 선분으로 넣기 (`bom/read_text/dash_split.py`)
**문제.** OCR이 양옆이 띄어진 `-`를 놓침 (`NUT(M8)  TYPE A`). 글자만 봐서는 빠진 자리를 모름 (공백이 1칸인 경우도 있음)

| 후보 | 장점 | 단점 |
|---|---|---|
| OCR 결과에서 빠졌는지 판단해 채움 | OCR이 읽은 `-`는 그대로 | OCR은 글자별 위치를 안 줌 → 어디가 빠졌는지 모름 |
| **떨어진 `-`는 선분으로 찾아 그 자리에서 자르고, 조각만 OCR** | 빠졌는지 판단할 필요 없음. 위치는 좌표, 글자는 OCR 원칙 그대로 | OCR 호출이 조금 늘어남 |

- 근거 (샘플 0601~0820 품명 2761칸): `-` 선분 개수 = 정답 `-` 개수 전부 일치, 떨어진 `-` 개수 = 정답 ` - ` 개수 전부 일치
- 떨어짐 = 가로 획 하나, 길이 `DASH_LEN` 안(실측 1.0~1.1), 양옆 간격 > 0.4 (글자 사이 0.2, 띄어쓰기 1.0~1.2, 머리글 0.69). 줄 끝은 떨어진 것으로
- 넣는 글자도 간격으로: 양옆 띄어쓰기면 `" - "`, 줄 끝 쪽은 공백 없이 (줄 잇기가 정함)
- 붙은 `-`(`ASSY-RH`)는 안 자름: OCR이 잘 읽음

**결과.** 품명 99.5% → **99.8%** (2756/2761), 고쳐진 8칸 외 바뀐 칸 없음. 남은 5칸은 모두 `DLX` → `OLX`

~~결정. 지금은 미세조정하지 않는다.~~ (남은 오류가 좌표 규칙·그림 확인으로 풀리거나, 학습으로도 풀리지 않는 것뿐이라 봄)

**결정 변경 (2026-11-26). 미세조정한다.** `DLX`→`OLX` 5칸은 그림이 깨끗한 순수 오독. 규칙(`OLX`→`DLX`)은 본 단어만 고쳐 다른 단어에서 또 틀림 → 학습으로 `D` 모양 자체를 배우게 함. 계획은 [OCR 23](../OCR/23_학습_계획.md), 틀린 걸 알아채는 비교(합의)는 [OCR 22](../OCR/22_합의와_점수.md)

## 3. 입력 그림
| 후보 | 장점 | 단점 |
|---|---|---|
| PDF clip 렌더링 | 간단 | 취소선·삼각형이 같이 찍힘 |
| **남은 획만 직접 그리기** | 4-1·4-2에서 찾은 선을 빼면 깨끗함 | 그리는 코드 필요 |

**결정.** 남은 획만 직접 그린다. **4-3(선 지우기)은 따로 단계로 두지 않고 여기에 합친다.** 선 굵기·해상도·여백은 구현 때 정한다.

## 4. 엔진

| CAD 선 폰트 | 낯선 글씨체에 강한 편 | 낯선 모양에 약한 편 (선을 굵게 그리면 나아짐) | RapidOCR |
| 눌러 쓴 긴 품명 | 눌린 글씨도 학습됨 | 많이 눌리면 뭉개짐 | RapidOCR |
| 한 글자 칸 | 기본 모델은 중국어 포함 → `-`를 `一`로 읽을 위험 | 한 글자는 빈칸·오독이 잦음 | 둘 다 약함 (사전이 맡음) |
| 허용 글자 제한 | 기본 ✗, 영어 전용 모델 + 글자 목록 파일로 해결 가능 | ✓ `tessedit_char_whitelist` | Tesseract |
| 띄어쓰기 | 중국어 모델은 공백을 빼먹기도, 영어 모델은 괜찮음 | 단어 단위라 강함 | Tesseract |
| 속도 | 프로세스 안, 여러 장 묶어 처리 | 줄마다 프로그램을 띄움 (호출당 수십 ms 추가) | RapidOCR |
| 설치·배포 | `uv add`만 | 프로그램 따로 설치, 실제 쓸 PC에도 | RapidOCR |
| 미세조정 | PaddleOCR로 학습 → 변환 | tesstrain, Windows에서 매우 번거로움 | RapidOCR |
- 제외: EasyOCR (PyTorch 수백 MB, 느림), PaddleOCR (RapidOCR과 같은 모델에 가장 무거움, 미세조정할 때 다시), 클라우드 OCR (외부 전송)
- 둘 다 못 푸는 것: `0`/`O`(모양이 같음), `1`/`I`·`5`/`S`·`8`/`B` → 품번 형식 규칙·사전과 교차 확인

**결정. RapidOCR (영어 전용 인식 모델).**
- OCR이 필요한 곳(긴 품명)이 RapidOCR이 강한 쪽
- 속도·설치·미세조정이 유리. 미세조정 데이터는 샘플 줄 그림 + json으로 바로 만들 수 있음 (4-1 줄 나누기)
- Tesseract의 장점(허용 글자, 띄어쓰기)은 영어 전용 모델로 대부분 메워짐
- `bom/read_text/ocr.py`는 엔진을 바꿀 수 있게 만든다. 결과가 기대 이하면 Tesseract를 붙여 비교
- 구현 때 확인: 영어 전용 모델·글자 목록 지정 방법, 한 글자 칸 결과, 공백 처리

## 5. 미세조정 (샘플로 OCR 학습)
**문제.** 학습 전 모델이 이 CAD 폰트(팔각형 `0`, 눌러 쓴 품명)를 얼마나 읽을지 모른다. 정답 붙은 도면 820개가 있다.

**결정. 칸 모드·줄 모드 측정 뒤, 틀리는 유형을 보고 정한다.**
- 학습 데이터: 줄 그림 + json 글자, 사람 손 없이 만듦. 0001~0600 학습 / 0601~0820 시험 (사전과 같은 나누기)
- 인식 모델은 줄 단위로 학습 → 두 줄 품명은 json 글자를 줄마다 나눠야 함 (줄 나누기가 다시 필요)
- 도구: PaddleOCR로 학습 → ONNX로 바꿔 RapidOCR에 넣음 (설치가 무겁고 GPU 없으면 느림)
- `CLAUDE.md`의 "글자 직접 학습은 보류"는 글자 인식기를 처음부터 만드는 일. 기존 모델을 다듬는 이것과는 다름 (진행하면 그 줄 수정)
