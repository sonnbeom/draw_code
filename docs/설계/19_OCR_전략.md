# 19. OCR 전략: 읽는 단위·입력·사전과 비교

> 5단계. 앞 문서: [02](02_PDF구조와_OCR.md) 문제 3 (글자 읽기 = OCR), [15](15_전체_파이프라인.md) ⑥

## 문제 정의
- 4-1·4-2에서 만든 **글자 사전**이 이미 숫자·품번을 읽는다 (샘플 0601~0820)

  | 칸 | 사전 결과 |
  |---|---|
  | 수량 | 11935/11935 |
  | 품번 | 2761/2761 (0/O만 구분 못 함) |
  | 리비전 숫자 | 817/818 |
  | 품명 | 1138/2379 (긴 이름은 글자를 가로로 눌러 써서 안 맞음) |
- 정할 것: OCR을 어디에 쓸지, 한 번에 무엇을 읽힐지(단위), 입력 그림을 어떻게 만들지

## 1. OCR을 어디에 쓰나
| 후보 | 장점 | 단점 |
|---|---|---|
| 모든 칸 OCR | 읽는 방법이 한 가지 | 사전이 100% 맞히는 칸까지 OCR 오류 위험 |
| 사전이 못 읽는 칸만 OCR (품명·머리글·검수 칸) | 숫자·품번은 검증된 사전 | 읽는 방법이 두 가지 |

**결정.** 먼저 **모든 칸을 OCR로 읽고 사전과 같은 줄에서 비교**한 뒤 정한다. 모듈은 따로 만든다.
| 파일 | 하는 일 |
|---|---|
| `bom/cell_image.py` | 줄 그림 만들기 (취소선·삼각형·연결선을 뺀 획만) |
| `bom/ocr.py` | OCR 엔진 감싸기: 그림 → (글자, 자신감). 엔진을 바꿔도 여기만 고침 |
| `bom/glyph_reader.py` | 사전 읽기 (`glyphs.match_glyphs`를 줄 단위로) |
| `explore/compare_readers.py` | 샘플 0601~0820: 열별 정확도 OCR vs 사전 = json, 틀린 예시 |

## 2. 읽는 단위
예: 88500 품번 칸 `88600-NR480`
| 후보 | 장점 | 단점 |
|---|---|---|
| A. 글자 하나 | 글자별 결과 | 글자 나누기가 어려움 (`22`는 끝점 공유, 긴 품명은 겹침, [06](06_취소선.md)). 앞뒤 맥락이 없어 OCR이 약함. 호출 가장 많음 |
| **B. 칸 안의 한 줄** | 위치는 선 좌표로 이미 앎 → OCR은 읽기만. json이 칸 단위라 바로 비교. 사전·취소 판정(4-1)과 같은 단위 | 호출 수 = 줄 수 (여러 장을 묶어 보내 완화) |
| C. 표 전체 | 호출 1번 | OCR이 위치를 찾고 칸을 다시 배정해야 함. 이웃 칸 글자를 붙여 읽을 수 있음. 큰 표는 줄이면 글자가 작아짐 |
| D. 행 하나 | 중간 | 행 안에서 칸을 다시 나눠야 함. C의 단점이 작게 남고 얻는 게 없음 |

**결정. B (칸 안의 한 줄).**
- 위치(칸, 몇 번째 줄)는 선 좌표로 안다: `strokes_by_cell` → `split_text_lines`, 상위는 `parent_cells`, 리비전은 삼각형 안쪽
- OCR의 글자 위치 찾기(검출)는 쓰지 않고 인식만 쓴다
- 칸 값 조립: 한 줄 칸 = 그 줄, 두 줄 품명 = 위 + 공백 + 아래 (json 형식은 구현 때 확인), 취소 후 새 줄 칸은 4-1 판정으로 구분
- 구현 때 확인: 긴 품명이 칸 경계를 넘어 옆 칸에 그려진 경우가 있는지

## 3. 입력 그림
| 후보 | 장점 | 단점 |
|---|---|---|
| PDF clip 렌더링 | 간단 | 취소선·삼각형이 같이 찍힘 |
| **남은 획만 직접 그리기** | 4-1·4-2에서 찾은 선을 빼면 깨끗함 | 그리는 코드 필요 |

**결정.** 남은 획만 직접 그린다. **4-3(선 지우기)은 따로 단계로 두지 않고 여기에 합친다.** 선 굵기·해상도·여백은 구현 때 정한다.

## 4. 엔진
**조건.** CAD 선 폰트(가는 획, 팔각형 `0`) / OCR이 진짜 필요한 곳은 눌러 쓴 긴 품명 / 한 글자 칸(`1`, `-`)은 사전이 100% / 줄 수만 개 / 도면은 회사 자료라 밖으로 안 보냄

**후보 (예상, 이 폰트로 돌리기 전)**
| 조건 | RapidOCR | Tesseract 5 | 예상 우세 |
|---|---|---|---|
| 속 모델 | PP-OCR 인식 모델 (ONNX). 문서·사진·합성 글씨로 폭넓게 학습 | LSTM 줄 인식기. 인쇄 문서 폰트 위주 | |
| CAD 선 폰트 | 낯선 글씨체에 강한 편 | 낯선 모양에 약한 편 (선을 굵게 그리면 나아짐) | RapidOCR |
| 눌러 쓴 긴 품명 | 눌린 글씨도 학습됨 | 많이 눌리면 뭉개짐 | RapidOCR |
| 한 글자 칸 | 기본 모델은 중국어 포함 → `-`를 `一`로 읽을 위험 | 한 글자는 빈칸·오독이 잦음 | 둘 다 약함 (사전이 맡음) |
| 허용 글자 제한 | 기본 ✗, 영어 전용 모델 + 글자 목록 파일로 해결 가능 | ✓ `tessedit_char_whitelist` | Tesseract |
| 띄어쓰기 | 중국어 모델은 공백을 빼먹기도, 영어 모델은 괜찮음 | 단어 단위라 강함 | Tesseract |
| 속도 | 프로세스 안, 여러 장 묶어 처리 | 줄마다 프로그램을 띄움 (호출당 수십 ms 추가) | RapidOCR |
| 설치·배포 | `uv add`만 | 프로그램 따로 설치, 실제 쓸 PC에도 | RapidOCR |
| 미세조정 | PaddleOCR로 학습 → 변환 | tesstrain, Windows에서 매우 번거로움 | RapidOCR |
- 제외: EasyOCR (PyTorch 수백 MB, 느림), PaddleOCR (RapidOCR과 같은 모델에 가장 무거움, 미세조정할 때 다시), 클라우드 OCR (외부 전송)
- 둘 다 못 푸는 것: `0`/`O`(모양이 같음), `1`/`I`·`5`/`S`·`8`/`B` → 품번 형식 규칙·사전과 교차 확인

**결정. RapidOCR (영어 전용 인식 모델).**
- OCR이 필요한 곳(긴 품명)이 RapidOCR이 강한 쪽
- 속도·설치·미세조정이 유리. 미세조정 데이터는 샘플 줄 그림 + json으로 바로 만들 수 있음 (4-1 줄 나누기)
- Tesseract의 장점(허용 글자, 띄어쓰기)은 영어 전용 모델로 대부분 메워짐
- `bom/ocr.py`는 엔진을 바꿀 수 있게 만든다. 결과가 기대 이하면 Tesseract를 붙여 비교
- 구현 때 확인: 영어 전용 모델·글자 목록 지정 방법, 한 글자 칸 결과, 공백 처리
